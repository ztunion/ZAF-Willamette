# Willamette Python SDK Test Client

This component contains interactive command-line clients for validating direct
and proxied requests to supported AI providers through their official Python
SDKs.

It is intended for development and integration testing. It is not a production
SDK, a load-testing tool, or a replacement for provider-specific applications.

## Features

- Interactive multi-turn command-line conversations
- Streamed responses
- Direct provider testing with real API keys
- Willamette MITM Proxy testing with virtual API keys
- OpenAI, Anthropic, Gemini, and Hugging Face SDK examples
- Proxy and certificate configuration through environment variables

## Provider support

### Direct provider mode

All four scripts can call their providers directly when a valid real API key
and an available model are configured.

| Script | Provider | API key variable | Credential format |
|---|---|---|---|
| `openai_query.py` | OpenAI | `OPENAI_API_KEY` | Bearer token |
| `claude_query.py` | Anthropic | `ANTHROPIC_API_KEY` | `x-api-key` |
| `gemini_query.py` | Google Gemini | `GEMINI_API_KEY` | Query parameter or Google API-key header |
| `hf_query.py` | Hugging Face | `HF_TOKEN` | Bearer token |

### Willamette proxy mode

The imported MITM Proxy implementation currently replaces credentials from:

```http
Authorization: Bearer <virtual-key>
```

Expected proxy support:

| Provider | Proxy status | Notes |
|---|---|---|
| OpenAI | Supported | Uses a Bearer credential |
| Hugging Face | Supported | Uses a Bearer credential |
| Anthropic | Not yet supported | Requires `x-api-key` extraction and replacement |
| Gemini | Not yet supported in the imported implementation | Requires query-parameter or `x-goog-api-key` support |

A temporary Gemini query-parameter implementation was validated during
development, but it should not be treated as production support until reviewed
and integrated into the maintained MITM Proxy implementation.

## Known limitations

- Model identifiers are hard-coded in each script.
- Model availability depends on the provider account, region, and current SDK.
- There are no automated tests.
- There is no retry or backoff policy.
- Errors are printed as generic provider exceptions.
- The scripts do not separately classify proxy, TLS, authentication, quota, and
  model errors.
- The Anthropic script currently uses a Korean system prompt.
- Applications using certificate pinning may reject interception even after the
  Willamette CA is trusted.
- These scripts should not be used for performance or security testing.

## Prerequisites

- Python 3.11 or later
- pip
- A provider API key or a Willamette virtual key
- Network access to the selected provider
- Network access to the Willamette MITM Proxy for proxy-mode testing
- The public CA certificate generated by the exact proxy deployment being tested

## Install dependencies

From the `python-sdk` directory:

### Windows Command Prompt

```cmd
python -m venv .venv
.venv\Scripts\activate

python -m pip install --upgrade pip
pip install -r requirements.txt
```

### macOS or Linux

```bash
python3 -m venv .venv
source .venv/bin/activate

python -m pip install --upgrade pip
pip install -r requirements.txt
```

## Run directly against a provider

Set only the required real provider key. Do not set proxy variables.

### Windows Command Prompt

```cmd
set OPENAI_API_KEY=<real-openai-key>
python openai_query.py
```

Other scripts use:

```cmd
set HF_TOKEN=<real-hugging-face-token>
set ANTHROPIC_API_KEY=<real-anthropic-key>
set GEMINI_API_KEY=<real-gemini-key>
```

### macOS or Linux

```bash
export OPENAI_API_KEY="<real-openai-key>"
python openai_query.py
```

Other scripts use `HF_TOKEN`, `ANTHROPIC_API_KEY`, or `GEMINI_API_KEY`.

Type `exit` or `quit`, or press `Ctrl+C`, to end a session.

## Prepare the proxy CA certificate

Do not use a certificate copied from another proxy installation.

Follow:

[Generate, retrieve, verify, and install the Willamette CA](certificates/README.md)

The deployment process is:

1. Start mitmproxy with a persistent configuration directory.
2. Let mitmproxy generate a unique CA on first start, or install an approved
   custom CA.
3. Retrieve only the public CA certificate from that deployment.
4. Verify its SHA-256 fingerprint through a trusted channel.
5. Configure application-scoped or operating-system trust.
6. Recreate trust configuration whenever the deployment CA rotates.

## Configure proxy mode

After preparing the public certificate and combined CA bundle, configure the
proxy.

### Windows Command Prompt

```cmd
set HTTP_PROXY=http://<proxy-host>:18080
set HTTPS_PROXY=http://<proxy-host>:18080
set SSL_CERT_FILE=%CD%\certificates\willamette-ca-bundle.pem
set REQUESTS_CA_BUNDLE=%CD%\certificates\willamette-ca-bundle.pem
set NO_PROXY=localhost,127.0.0.1
```

### macOS or Linux

```bash
export HTTP_PROXY="http://<proxy-host>:18080"
export HTTPS_PROXY="http://<proxy-host>:18080"
export SSL_CERT_FILE="$PWD/certificates/willamette-ca-bundle.pem"
export REQUESTS_CA_BUNDLE="$PWD/certificates/willamette-ca-bundle.pem"
export NO_PROXY="localhost,127.0.0.1"
```

## Run through Willamette

Complete these steps first:

1. Start the CMS gRPC Service.
2. Create the provider key and policy through the CMS Console.
3. Start the Willamette MITM Proxy using a persistent CA configuration
   directory.
4. Retrieve and trust the public CA certificate from that proxy.
5. Configure the proxy and CA environment variables.
6. Set the provider environment variable to the Willamette virtual key.
7. Run the matching script.

Example for OpenAI on Windows:

```cmd
set OPENAI_API_KEY=<virtual-openai-key>
python openai_query.py
```

Example for Hugging Face on macOS or Linux:

```bash
export HF_TOKEN="<virtual-hugging-face-token>"
python hf_query.py
```

## Test procedure

Run each supported provider in both modes.

| Test | Credential | Proxy variables | Expected result |
|---|---|---|---|
| Direct | Real provider key | Unset | Provider returns a response |
| Proxy | Virtual key | Set | Proxy resolves the key and provider returns a response |
| Invalid virtual key | Unknown virtual key | Set | Request fails without exposing a real key |
| Missing certificate trust | Virtual key | Set, CA unset | TLS verification fails |
| Proxy unavailable | Virtual key | Set to unavailable host | Proxy connection fails |

For each test, record:

- script and provider;
- direct or proxy mode;
- configured model;
- HTTP or proxy error category;
- whether the CMS lookup succeeded;
- whether real credentials remained absent from logs.

## Troubleshooting

### `CERTIFICATE_VERIFY_FAILED`

- Confirm the CA came from the active proxy deployment.
- Verify its fingerprint with the proxy administrator.
- Recreate the combined CA bundle.
- Confirm `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` reference that bundle.
- Do not disable certificate verification.

### `ProxyError` or connection refused

- Confirm `<proxy-host>:18080` is reachable.
- Confirm the proxy service is running.
- Confirm firewall rules allow the test machine.
- Confirm the client is not using an obsolete proxy address.

### Provider authentication failure

- Confirm direct mode uses a real key.
- Confirm proxy mode uses a virtual key.
- Confirm the provider credential format is supported by the current proxy.
- Anthropic and Gemini are not supported by the imported Bearer-only proxy
  implementation.

### Model not found

The model constants are defined near the top of each script. Select a model
available to the configured provider account and SDK version.

## Security

- Never commit API keys or service-account credentials.
- Never commit deployment CA certificates or CA private keys.
- Verify the public CA fingerprint before trusting it.
- Keep the proxy configuration directory persistent and access-controlled.
- Restrict the proxy port to approved test networks or IP addresses.
- Do not log real or virtual credentials.
- Do not disable TLS verification.
- Remove test CAs from trust stores when no longer needed.
- Rotate any credential or CA private key that may have been exposed.
