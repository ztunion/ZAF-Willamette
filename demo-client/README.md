# Willamette Demo Client

The Willamette Demo Client is a small Tkinter desktop application used to test
AI-provider requests directly and through the Willamette MITM proxy.

It is a development and demonstration tool. It is not intended to be a
production chat client or a secure credential vault.

## What this component does

The client supports two request paths:

```text
Direct Provider mode
Real provider key -> AI provider
```

```text
Willamette Proxy mode
Virtual key -> MITM proxy -> CMS key resolution -> AI provider
```

The same UI is used for both paths, making it easier to compare a direct request
with the equivalent proxied request.

## Supported providers

| Provider | Endpoint used by the client | Credential format sent by the client |
|---|---|---|
| OpenAI | Chat Completions API | `Authorization: Bearer <key>` |
| Anthropic | Messages API | `x-api-key: <key>` |
| Gemini | Generative Language API | `?key=<key>` query parameter |
| Hugging Face | Router chat-completions endpoint | `Authorization: Bearer <key>` |

The client knows how to construct requests for all four providers. Successful
virtual-key replacement in proxy mode depends on the credential formats
implemented by the currently deployed MITM plugin.

For example, a MITM build that replaces only Bearer credentials can process the
OpenAI and Hugging Face formats, but not Anthropic `x-api-key` or Gemini query
keys. Confirm the MITM feature set before treating a proxy-mode failure as a
client failure.

## Supported functionality

| Capability | Status | Notes |
|---|---|---|
| Direct provider testing | Supported | Uses a real provider key. |
| Willamette proxy testing | Supported | Uses a virtual key and configurable proxy URL. |
| Provider selection | Supported | OpenAI, Anthropic, Gemini, and Hugging Face. |
| Editable model name | Supported | Change the model when a default model is unavailable. |
| API-key show/hide | Supported | Key is held only in process memory. |
| Chat-style display | Supported | Displays one request result at a time in a running transcript. |
| Background request thread | Supported | Prevents the UI from freezing during network calls. |
| Windows executable build | Supported | PyInstaller configuration is included. |
| macOS application build | Supported | Must be built on macOS. |

## Not currently supported

The client does not provide:

- streaming responses;
- persistent conversation history;
- multi-turn provider context between requests;
- secure local key storage;
- OAuth or service-account authentication;
- image, audio, file, or tool-call inputs;
- proxy authentication;
- retry or backoff logic;
- provider usage or cost reporting;
- certificate installation or validation for the MITM proxy;
- automatic model discovery;
- automatic virtual-key creation.

Proxy mode currently sets TLS verification to `False`. This avoids certificate
errors during MITM testing, but it also disables server-certificate validation.
Use this behavior only in a controlled development environment. A production
client should trust an explicitly installed proxy CA and keep certificate
verification enabled.

## Prerequisites

- Python 3.10 or later;
- `requests`;
- Tkinter;
- internet access to the selected provider;
- a real provider key for direct mode;
- a Willamette virtual key and reachable MITM proxy for proxy mode.

Tkinter is included with most Windows and macOS Python installations. On some
Linux distributions it must be installed separately, for example with the
system package `python3-tk`.

## Local setup

### 1. Create and activate a virtual environment

Windows Command Prompt:

```cmd
python -m venv .venv
.venv\Scripts\activate
```

macOS or Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

```bash
pip install requests
```


```bash
python app.py
```

## How to use the client

### Direct Provider mode

1. Select **Direct Provider**.
2. Select the provider.
3. Confirm or change the model name.
4. Enter a real provider API key or token.
5. Enter a test message.
6. Select **Send**.
7. Confirm the provider returns a successful response.

Direct mode should be tested first. It proves that the provider key, model, and
request body are valid before the MITM proxy is introduced.

### Willamette Proxy mode

1. Select **Willamette Proxy**.
2. Select the provider.
3. Enter the proxy URL.
4. Confirm or change the model name.
5. Enter the virtual API key generated by the CMS Console.
6. Enter the same test message used in direct mode.
7. Select **Send**.
8. Confirm the response succeeds through the proxy.

The default proxy URL in the uploaded source is:

```text
http://34.95.56.239:18080
```

Treat this as a development default only. The field is editable in the UI.
Avoid hard-coding a public proxy address in production builds.

## Default models

The source includes default model names for convenience. Provider model names
and account access can change, so the model field is editable.

| Provider | Default in the uploaded source |
|---|---|
| OpenAI | `gpt-4o-mini` |
| Anthropic | `claude-3-5-haiku-latest` |
| Gemini | `gemini-1.5-flash` |
| Hugging Face | `openai/gpt-oss-120b:fastest` |

A `404`, model-not-found error, or access error can mean the model is retired,
renamed, unavailable in the account, or unsupported by that provider endpoint.
Enter a model that is currently available to the test account.

## Test procedure

Use a harmless prompt such as:

```text
Reply with exactly: Willamette test passed
```

For each provider:

1. Run the request in Direct Provider mode with the real key.
2. Record whether the provider, model, and account are valid.
3. Create or locate the matching virtual key in the CMS Console.
4. Run the same request in Willamette Proxy mode.
5. Compare the two responses.
6. Review MITM logs to confirm the credential was detected and replaced.
7. Review CMS logs to confirm the virtual key was resolved.
8. Confirm that logs do not contain the complete real provider key.

### Interpreting failures

| Result | Likely meaning |
|---|---|
| Direct mode fails | Provider key, endpoint, model, account access, or request payload is invalid. |
| Direct succeeds but proxy returns the virtual key to the provider | MITM did not recognize or replace that credential format. |
| Proxy returns `401` with an OAuth-token message for Gemini | Gemini API keys were sent as Bearer tokens or not replaced correctly. |
| Proxy returns model-not-found | Key replacement may have worked, but the configured model is unavailable. |
| TLS warning appears | Expected with the current `verify=False` demo configuration. |
| Connection refused or timeout | Proxy address, firewall, proxy process, or network path is unavailable. |

## Build a Windows executable

Build on Windows from the client directory:

```cmd
python -m PyInstaller --onefile --windowed --name WillametteDemoClient app.py
```

Output:

```text
dist\WillametteDemoClient.exe
```

The included spec file can also be used:

```cmd
python -m PyInstaller WillametteDemoClient.spec
```

Do not commit generated `build`, `dist`, `.venv`, or `__pycache__` directories.

## Build a macOS application

Build on macOS. A Windows build cannot produce a reliable macOS application.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install requests pyinstaller
python -m PyInstaller --windowed --name WillametteDemoClient app.py
```

Output:

```text
dist/WillametteDemoClient.app
```

Create a ZIP that preserves the macOS application bundle metadata:

```bash
cd dist
ditto -c -k --sequesterRsrc --keepParent \
  WillametteDemoClient.app \
  WillametteDemoClient-mac.zip
```

Unsigned macOS builds may be blocked by Gatekeeper. Production distribution
requires the organization's code-signing and notarization process.

## Google Cloud deployment

The Demo Client is a desktop application and is not deployed to Google Cloud.

## Troubleshooting

### `ModuleNotFoundError: requests`

```bash
pip install requests
```

### Tkinter is missing

Install a Python distribution that includes Tkinter or install the operating
system's Tk package.

### Provider returns `401` or `403`

Confirm whether the current mode expects a real key or a virtual key. In direct
mode, use the real provider key. In proxy mode, use the CMS-generated virtual
key.

### Gemini returns `ACCESS_TOKEN_TYPE_UNSUPPORTED`

Gemini API-key authentication is not an OAuth Bearer token. The client sends the
key in the URL query parameter. Confirm that the MITM plugin extracts and
replaces the Gemini query key rather than converting it to a Bearer token.

### Model is unavailable

Change the value in the Model field to one available to the provider account.

### Proxy cannot be reached

Check:

- the proxy URL and port;
- the proxy service status;
- firewall source ranges;
- whether the test machine is allowed to connect;
- whether the proxy supports the selected provider's credential location.

## Security notes

- Never commit provider keys or virtual keys.
- Do not share screenshots with visible key values.
- Rotate keys that appear in logs, chat, shell history, or screenshots.
- Use the **Show** option only when necessary.
- Do not use `verify=False` outside a controlled test environment.
- Restrict access to development MITM proxy ports; do not leave them open to
  the entire internet.
